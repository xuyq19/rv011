# Linux 0.11 移植到 RISC-V（rv32）完整步骤

本文按实际移植顺序，把整个移植过程拆成 12 个阶段。每个阶段包含四部分：

1. **目标**：本阶段完成后系统具备什么能力；
2. **涉及文件**：本阶段要新建/修改哪些文件；
3. **具体操作**：逐条列出改动内容，引用仓库中真实存在的文件与关键代码；
4. **验证方法**：编译、运行、看什么输出，判定是否成功。

文中所有相对路径均以 `linux-0.11/` 为基准（例如 `boot/head.s` 指
`linux-0.11/boot/head.s`）。命令分两种：宿主机命令（`$` 前缀）和内核
启动后 shell 内命令（`sh#` 前缀）。

## 0. 背景与目标

Linux 0.11（1991 年）是经典的教学内核：约 1.5 万行 C/汇编，x86 私有
代码（启动、中断、页表、串口）和架构无关代码（文件系统、进程、调度）
边界清晰。移植工作就是把 x86 私有部分替换为 RISC-V 实现，架构无关
部分尽量保持原样。

本工程的目标形态：

| 项目 | 配置 |
|---|---|
| 目标架构 | rv32imafdc_zicsr_zifencei / ilp32d |
| 特权模式 | 内核运行于 M-mode，用户程序运行于 U-mode |
| 分页 | Sv32 两级页表 |
| 虚拟平台 | QEMU `virt`（riscv32），128 MB 内存 |
| 根文件系统 | Minix v1 ramdisk（2 MB，嵌入内核镜像） |
| 启动方式 | `-bios none -kernel kernel.elf`，不依赖 OpenSBI/SBI |

最终产物：一个 `kernel.elf`，内含内核、ramdisk 根文件系统和全部用户
程序，QEMU 直接启动到 shell。

## 1. 阶段零：环境准备

### 1.1 目标

宿主机具备编译 rv32 代码的交叉工具链和运行 RISC-V 虚拟机的 QEMU。

### 1.2 涉及文件

无（纯环境安装）。

### 1.3 具体操作

**第 1 步：安装交叉工具链。** Ubuntu 上直接使用发行版自带的
`riscv64-unknown-elf` 工具链（自带 rv32 multilib）：

```sh
sudo apt-get update
sudo apt-get install -y gcc-riscv64-unknown-elf
```

如果发行版没有该软件包，可下载 riscv-gnu-toolchain 官方预编译
release 并解压到 `/opt/riscv`，把 `/opt/riscv/bin` 加入 `PATH`。
工程 CI（`.github/workflows/build.yml`）采用的正是“先 apt、缺包再
下载预编译包”的兜底策略。

**第 2 步：验证 rv32 multilib 可用。** 仅安装工具链不够，还要确认它能
编译 rv32 目标（部分工具链默认只带 rv64 multilib）：

```sh
echo 'int main(void){return 0;}' > /tmp/t.c
riscv64-unknown-elf-gcc -march=rv32imafdc_zicsr_zifencei \
  -mabi=ilp32d -c /tmp/t.c -o /tmp/t.o
file /tmp/t.o
```

预期输出包含 `ELF 32-bit LSB ... UCB RISC-V`。若报
`cannot find multilib` 一类的错误，说明工具链缺少 rv32 multilib，
需要换工具链来源。

**第 3 步：安装 QEMU。**

```sh
sudo apt-get install -y qemu-system-misc
qemu-system-riscv32 --version
```

工程验证环境为 QEMU 8.2.2。QEMU 的 `virt` 机器提供：UART（16550，
地址 `0x10000000`）、CLINT 定时器（基址 `0x02000000`）、PLIC（本工程
未使用，全部设备采用轮询）。

**第 4 步：获取 Linux 0.11 源码。**

官方历史版本在 kernel.org：

```sh
wget https://www.kernel.org/pub/linux/kernel/Historic/old-versions/linux-0.11.tar.gz
tar xzf linux-0.11.tar.gz
```

仓库中的 `3ab7550`（Initial commit）即包含该官方源码；后续提交逐个
加入 RISC-V 移植改动，最终形态可直接 `git log` 查看。

## 2. 阶段一：搭建工程骨架

### 2.1 目标

把 x86 的 `boot/bootsect.s`、`boot/setup.s`、`boot/head.s` 启动链
替换为 RISC-V 单镜像启动，建立 `Makefile` 和链接脚本，让
`make` 能产出 `kernel.elf`。

### 2.2 涉及文件

| 文件 | 作用 |
|---|---|
| `kernel.ld` | 链接脚本：镜像从 `0x80000000` 布局 |
| `Makefile` | 统一构建内核、用户程序、rootfs |
| `boot/head.s` | RISC-V 启动入口（替代原 x86 head.s） |
| `include/linux/head.h` | 机器地址常量（RAM/UART/CLINT） |

### 2.3 具体操作

**第 1 步：定义机器地址常量**（`include/linux/head.h`）。QEMU virt
机器的关键地址：

```c
#define RAM_BASE        0x80000000UL   /* QEMU 加载内核的物理地址 */
#define RAM_SIZE        (128*1024*1024)
#define RAM_END         (RAM_BASE + RAM_SIZE)
#define UART_BASE       0x10000000UL   /* 16550 串口 */
#define CLINT_BASE      0x02000000UL
#define CLINT_MTIME     (*(volatile unsigned long *)(CLINT_BASE + 0xBFF8))
#define CLINT_MTIMECMP  (*(volatile unsigned long *)(CLINT_BASE + 0x4000))
#define CLINT_TIMEBASE  10000000UL     /* 10 MHz */
#define USER_LIMIT      0x80000000UL   /* 用户虚拟地址上限 */
```

**第 2 步：编写链接脚本**（`kernel.ld`）。x86 0.11 用 `bootsect +
setup + system` 三段式，RISC-V 改成单 ELF：

```ld
OUTPUT_ARCH(riscv)
ENTRY(_start)

SECTIONS
{
	. = 0x80000000;
	.text : { *(.text.init) *(.text .text.*) }
	.rodata : { *(.rodata .rodata.*) }
	.data : { *(.data .data.*) }
	.rootfs : { KEEP(*(.rootfs)) }        /* ramdisk 镜像段 */
	.bss : {
		_bss_start = .;
		*(.bss .bss.*) *(COMMON)
		_bss_end = .;
	}
	. = ALIGN(4096);
	_kernel_end = .;
	end = _kernel_end;
	/DISCARD/ : { *(.comment) *(.riscv.attributes) *(.note*) }
}
```

要点：入口符号是 `_start`；`_kernel_end` 供内存管理计算可用物理内存
起点；`.rootfs` 段专门放后面要嵌入的 ramdisk 镜像。

**第 3 步：编写启动入口**（`boot/head.s`）。QEMU 把内核加载到
`0x80000000` 后以 M-mode 执行，入口要做四件事：

```asm
.section .text.init,"ax",@progbits
.globl _start
_start:
	# 1) 清零 .bss
	la t0, _bss_start
	la t1, _bss_end
	beq t0, t1, 2f
1:	sw zero, 0(t0)
	addi t0, t0, 4
	bltu t0, t1, 1b
2:	# 2) 建立引导栈，并保存到 mscratch
	la sp, _stack_top
	csrw mscratch, sp
	# 3) 配置 PMP：允许 S/U 模式访问全部内存
	li t0, -1
	csrw pmpaddr0, t0
	li t0, 0x0f              # TOR, R|W|X
	csrw pmpcfg0, t0
	sfence.vma
	# 4) 跳入 C 入口
	call main
3:	wfi
	j 3b
```

**第 4 步：编写 Makefile。** 使用 `riscv64-unknown-elf-gcc` 作为编译
器和链接器，统一传入 `-march=rv32imafdc_zicsr_zifencei -mabi=ilp32d`
（`MARCH` 变量），并定义 `run` 目标：

```make
CROSS = riscv64-unknown-elf-
MARCH = -march=rv32imafdc_zicsr_zifencei -mabi=ilp32d
KCFLAGS = -O2 -Wall -fno-pic -mno-relax -ffreestanding -fgnu89-inline \
	-fno-builtin -nostdinc -Iinclude $(MARCH)

kernel.elf: $(KOBJS) rootfs.o kernel.ld
	$(LD) $(LDFLAGS) -T kernel.ld -o $@ $(KOBJS) rootfs.o

run: kernel.elf
	qemu-system-riscv32 -M virt -m 128M -bios none -kernel kernel.elf \
		-nographic -no-reboot
```

### 2.4 验证方法

```sh
make -j2
file kernel.elf
```

预期：`kernel.elf: ELF 32-bit LSB executable, UCB RISC-V`。此时内核
还没有任何输出，下一步先点亮串口。

## 3. 阶段二：最小启动与串口输出

### 3.1 目标

内核在 QEMU 中启动，从 16550 UART 输出字符；`printk`/`printf` 输出
重定向到串口，可以看到内核启动信息。

### 3.2 涉及文件

| 文件 | 作用 |
|---|---|
| `kernel/chr_drv/console.c` | 16550 UART 初始化、轮询收发 |
| `kernel/printk.c`、`kernel/vsprintf.c` | 格式化输出（沿用原版） |
| `init/main.c` | C 入口，先调用 `uart_init()` |

### 3.3 具体操作

**第 1 步：实现 16550 驱动**（`kernel/chr_drv/console.c`）。QEMU virt
的串口是标准的 16550，寄存器是 8 位端口，映射在内存地址
`0x10000000`：

```c
#define UART_THR  (UART_BASE + 0)   /* 发送保持寄存器 */
#define UART_RBR  (UART_BASE + 0)   /* 接收缓冲寄存器 */
#define UART_FCR  (UART_BASE + 2)   /* FIFO 控制 */
#define UART_LCR  (UART_BASE + 3)   /* 线路控制：8N1 */
#define UART_LSR  (UART_BASE + 5)   /* 线路状态 */

void uart_init(void)
{
	outb(0x03, UART_LCR);   /* 8 数据位，无校验，1 停止位 */
	outb(0x01, UART_FCR);   /* 使能 FIFO */
}

/* 轮询发送：等待发送保持寄存器空（LSR bit5） */
static void uart_putc(char c)
{
	while (!(inb(UART_LSR) & 0x20))
		;
	outb(c, UART_THR);
}
```

这里需要 x86 的 `outb/inb`。本工程在 `include/asm/io.h` 里用
`*(volatile unsigned char *)` 重新实现为内存映射 I/O，原 x86 的
`inb_p/outb_p` 保留为普通字节读写（不加延迟，QEMU 不需要 I/O 等待）。

**第 2 步：把 `\n` 展开为 `\n\r`。** 0.11 的终端输出假定 tty 处理
换行；在串口驱动里直接输出 `\n` 会被 QEMU 显示为“回车但不换行”。
`con_write`（tty 写回调）中遇到 `\n` 时补一个 `\r`，这是老终端语义，
也是 0.11 原版 console 的行为。

**第 3 步：接线。** `init/main.c` 的 `main()` 开头调用
`uart_init()`，`printk`（`kernel/printk.c`）仍然调用 `tty_write`，
最终落到 `con_write`。这样后续所有 `printk` 自动从串口出来，不需要
改动打印逻辑。

### 3.4 验证方法

在 `main()` 里加一句临时 `printk`（例如
`printk("Hello from rv011\n\r")`），然后：

```sh
make -j2
make run
```

预期：串口出现该字符串，之后进入 `for(;;) pause()` 循环（此时还没有
时钟，表现为“卡住”是正常的，下一阶段解决）。

### 3.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 完全没有输出 | UART 未初始化，或输出函数在等 LSR 位 | 检查 `uart_init()` 是否在首次输出前调用 |
| 输出“回车不换行” | 只输出 `\n` | 在 `con_write` 中把 `\n` 扩展为 `\n\r` |

## 4. 阶段三：trap 框架（异常/中断统一入口）

### 4.1 目标

所有异常和中断进入统一入口 `trap_entry`（`mtvec` 指向它），保存完整
现场（trapframe），交给 C 函数 `trap_handler()` 分发，返回后恢复现场
并 `mret`。用户态 trap 要换到内核栈，内核态 trap 在当前栈压帧。

### 4.2 涉及文件

| 文件 | 作用 |
|---|---|
| `include/linux/sched.h` | `struct trapframe` 布局 |
| `kernel/trap.S` | `trap_entry`/`ret_from_trap`/`switch_to` |
| `kernel/traps.c` | `trap_handler()` 分发、`trap_init()` |

### 4.3 具体操作

**第 1 步：定义 trapframe**（`include/linux/sched.h`）。x86 0.11 用
硬件压栈保存现场，RISC-V 需要自己定义保存格式：

```c
struct trapframe {
	unsigned long mstatus;      /* 0   */
	unsigned long mepc;         /* 4   */
	unsigned long ra, sp;       /* 8..12 */
	/* ... x2..x31，共 32 个通用寄存器 */
	unsigned long mcause;       /* 132 */
	unsigned long from_user;    /* 136 */
	unsigned long long f[32];   /* 140..396：f0-f31（64 位） */
	unsigned long fcsr;         /* 396 */
};                              /* 共 400 字节 */
```

浮点部分在阶段九加入；trap.S 与 sched.h 中的偏移量（`TF_MSTATUS`、
`TF_MEPC`、`TF_FCSR`、`TF_SIZE`）必须保持一致。

**第 2 步：实现 `trap_entry`**（`kernel/trap.S`）。核心逻辑：

- 用 `mscratch` 区分来源：进入时读 `mstatus` 的 MPP 位判断是否来自
  U-mode。若是用户态，交换 `sp` 与 `mscratch`（内核栈），置
  `from_user=1`；若是内核态，直接在当前栈压帧；
- 保存 mstatus、mepc、全部通用寄存器到 trapframe；
- 读 mcause，调用 `trap_handler(tf)`；
- 返回后按 `from_user` 决定是否切回用户栈，恢复寄存器，`mret`。

关键指令：

```asm
	csrr t0, mstatus       # 读回初始 mstatus
	sw   t0, TF_MSTATUS(sp)
	csrr t1, mepc
	sw   t1, TF_MEPC(sp)
	# ... 保存 x1..x31 ...
	csrr t1, mcause
	sw   t1, TF_MCAUSE(sp)
	call trap_handler
	lw   t0, TF_MSTATUS(sp)
	csrw mstatus, t0
	lw   t0, TF_MEPC(sp)
	csrw mepc, t0
	mret
```

**第 3 步：实现 `trap_handler()`**（`kernel/traps.c`）。按 mcause
分发，后续阶段逐步填充分支：

```c
void trap_handler(struct trapframe * tf)
{
	unsigned long cause = tf->mcause;
	int from_user = tf->from_user;

	if ((cause & 0x80000000) && (cause & 0xff) == 7) {
		/* 机器定时器中断：阶段四 */
	} else switch (cause) {
	case 8:  /* ecall from U-mode */
	case 11: /* ecall from M-mode（内核库） */
		/* 系统调用：阶段六 */
		break;
	case 12: /* 取指/读页错误 */
	case 15: /* 写页错误 */
		/* 页错误处理：阶段五 */
		break;
	default:
		exception_trap(tf, cause);  /* 打印现场后停机/循环 */
		break;
	}
}

void trap_init(void)
{
	__asm__ volatile ("csrw mtvec, %0" :: "r" (trap_entry));
}
```

`exception_trap()` 打印 cause、mepc、mtval 和 ra/sp，方便对照
RISC-V 特权手册查异常码（例如 1=取指访问错、5=取指页错误、7=存储
页错误、2=非法指令）。

### 4.4 验证方法

在 `main()` 里故意触发一个非法指令（例如 `.word 0xdeadbeef`），
`make run` 后应看到 `exception_trap` 打印 cause=2 和 mepc 地址，
而不是整个 QEMU 崩溃。验证完删掉该行。

### 4.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户态首条指令取指异常 | 页表项编码错误（阶段五详述） | 按 Sv32 格式编码 PPN |
| 用户态访问内存被拒绝 | PMP 未配置 | 启动早期 `pmpaddr0=-1, pmpcfg0=0x0f` |
| 嵌套中断覆盖现场 | 内核态 trap 在栈顶压帧 | 内核态 trap 在当前 `sp` 压帧，不切换栈 |

## 5. 阶段四：CLINT 定时器与调度

### 5.1 目标

产生周期性定时器中断：`jiffies` 递增、`do_timer()` 更新进程时间片并
触发调度，让多任务可以跑起来。

### 5.2 涉及文件

| 文件 | 作用 |
|---|---|
| `kernel/traps.c` | 定时器中断分支（jiffies++、重新装载 mtimecmp） |
| `kernel/sched.c` | `do_timer()`、`sched_init()` |
| `include/linux/sched.h` | `HZ`、`TIMER_INTERVAL`、`jiffies` |

### 5.3 具体操作

**第 1 步：了解 CLINT。** QEMU virt 的 CLINT 提供 64 位
`mtime`（`0x0200BFF8`，10 MHz 递增）和每 hart 一个
`mtimecmp`（hart0 在 `0x02004000`）。当 `mtime >= mtimecmp` 时产生
机器定时器中断。

**第 2 步：在 trap_handler 中处理定时器中断**（`kernel/traps.c`）：

```c
if ((cause & 0x80000000) && (cause & 0xff) == 7) {
	jiffies++;
	CLINT_MTIMECMP = CLINT_MTIME + TIMER_INTERVAL;  /* 重装载 */
	do_timer(from_user);
	if (from_user)
		do_signals(tf);
	return;
}
```

`jiffies++` 必须在重装载前完成，且每个中断周期恰好加一次。若漏加，
`times()`/`alarm()` 等时钟类系统调用全部失效（本工程踩过此坑）。

**第 3 步：定义节拍**（`include/linux/sched.h`）：`HZ=100`，
`TIMER_INTERVAL = CLINT_TIMEBASE / HZ = 100000`（10 ms）。

**第 4 步：`sched_init()`**（`kernel/sched.c`）初始化定时器：

```c
void sched_init(void)
{
	int i;
	for (i = 1; i < NR_TASKS; i++)
		task[i] = NULL;
	CLINT_MTIMECMP = CLINT_MTIME + (CLINT_TIMEBASE / HZ);
	__asm__ volatile ("li t0, 0x80; csrs mie, t0"); /* MTIE */
}
```

`mie` 的 bit7 是 MTIE（机器定时器中断使能）。`mstatus.MIE` 初始为 0，
`main()` 在完成所有初始化后调用 `sti()` 打开全局中断。

### 5.4 验证方法

跑 `t_up` 或在 init 里打印 `jiffies` 两次，间隔应递增；再验证
`alarm(1)` 约 1 秒后触发 SIGALRM。

## 6. 阶段五：物理内存管理与 Sv32 分页

### 6.1 目标

实现物理页分配/释放（`mem_map`），为用户任务建立 Sv32 页表，内核
通过 `translate_user()` 访问用户地址，fork 采用写时复制（COW）。

### 6.2 涉及文件

| 文件 | 作用 |
|---|---|
| `mm/memory.c` | `mem_map`、页表建立、COW、`translate_user()` |
| `include/linux/mm.h` | `phys_ppn()`/`pte_phys()` 编码解码、PTE 位定义 |
| `include/linux/head.h` | `USER_LIMIT` 等常量 |
| `kernel/fork.c` | fork 时复制页表（COW 标记） |

### 6.3 具体操作

**第 1 步：物理页管理。** 用 `mem_map[]` 数组记录每页引用计数
（`MAP_NR(addr)=(addr-RAM_BASE)>>12`），`get_free_page()` 找空页并
清零，`free_page()` 递减计数。注意内存边界检查：地址低于 `RAM_BASE`
或高于 `RAM_END` 时不能释放。

**第 2 步：理解 Sv32 页表项格式（本移植最大的坑）。**
Sv32 的两级页表：页目录 1024 项（VPN[1]，bits[31:22]）→ 页表 1024
项（VPN[0]，bits[21:12]）→ 4 KB 页。页表项（PTE）布局：

| 位 | 含义 |
|---|---|
| 0 | V（有效） |
| 1 | R（读） |
| 2 | W（写） |
| 3 | X（执行） |
| 4 | U（用户可访问） |
| 5 | G（全局） |
| 6 | A（已访问） |
| 7 | D（已修改） |
| 10-31 | PPN（物理页号，即 `phys >> 12`） |

所以 PTE 必须编码为 `(phys >> 12) << 10 | flags`。若直接把物理地址
写进 PTE，内核自己查表时自洽（`pte_phys()` 按同样规则解码），但硬件
翻译结果错误——Sv32 硬件只认 bits[10:31] 里的 PPN。现象是用户态
首条指令取指异常（cause=5）。本工程在 `include/linux/mm.h` 提供两个
辅助函数，所有读写 PTE 的地方统一使用：

```c
#define PTE_V      0x001
#define PTE_R      0x002
#define PTE_W      0x004
#define PTE_X      0x008
#define PTE_U      0x010
#define PTE_A      0x040
#define PTE_D      0x080
#define PTE_USER_RW    (PTE_V | PTE_R | PTE_W | PTE_U | PTE_A | PTE_D)
#define PTE_USER_RWX   (PTE_V | PTE_R | PTE_W | PTE_X | PTE_U | PTE_A | PTE_D)

static inline unsigned long phys_ppn(unsigned long phys)
{ return ((phys >> 12) << 10); }

static inline unsigned long pte_phys(unsigned long pte)
{ return ((pte >> 10) & 0x3fffff) << 12; }
```

**第 3 步：建立页表。** `get_empty_page(address)` 分配页目录项指向
新页表，再把用户物理页映射为 `PTE_USER_RWX`；`free_page_tables()`
逐级遍历页目录/页表并释放。内核在 M-mode 无翻译运行，页表只为用户
态服务，因此不需要 x86 的段/页寄存器切换，`switch_to` 时只换
`task->pgdir` 指针。

**第 4 步：COW fork。** `copy_page_tables()` 复制页目录和页表项，
把用户页清除 W 位并递增 `mem_map` 引用计数；写保护页触发 store page
fault（cause=15），`un_wp_page()` 分配新页、复制内容、恢复 W 位：

```c
/* mm/memory.c，写保护页处理 */
this_page &= ~PTE_W;                 /* 父页去写 */
*table_entry = phys_ppn(new_page) | PTE_USER_RW;  /* 子页可写 */
```

注意内核在 M-mode 下写用户页时**不会**触发页错误（M-mode 不走地址
翻译），所以 `copy_to_user`/`memcpy_tofs` 系列必须显式走
`translate_user()`，否则会绕过 COW 直接改到共享页。

**第 5 步：`translate_user()`。** 给定用户虚拟地址，查当前任务的
页目录和页表，返回物理地址：

```c
/* mm/memory.c */
if (!pte || !(*pte & PTE_V) || !(*pte & PTE_U))
	return 0;               /* 无效或非用户页 */
return pte_phys(*pte) | (addr & 0xfff);
```

### 6.4 验证方法

用户程序能够执行（阶段七加载器就绪后）；`t_cow` 验证父子进程内存
隔离与堆增长；故意访问未映射地址应触发页错误打印而不是崩溃。

### 6.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户态取指异常 | PTE 未按 `(phys>>12)<<10` 编码 | 统一用 `phys_ppn()` |
| 用户程序读到错误数据 | 内核 M-mode 直写绕过 COW | 用户内存访问一律 `translate_user()` |
| 释放页 panic | 引用计数与映射不一致 | 检查 `copy_page_tables` 的计数递增 |

## 7. 阶段六：系统调用

### 7.1 目标

用户态 `ecall` 进入内核，按调用号执行对应 `sys_*` 函数并返回结果。

### 7.2 涉及文件

| 文件 | 作用 |
|---|---|
| `include/unistd.h` | `_syscall0/1/2/3` 宏、调用号定义 |
| `include/linux/sys.h` | `sys_call_table[]` |
| `kernel/traps.c` | ecall 分支：`mepc+=4`、查表 |
| `lib/*.c` | write/read/fork 等用户态封装 |

### 7.3 具体操作

**第 1 步：确定 ABI。** 本工程沿用 Linux 0.11 的系统调用编号（0-72，
共 73 个），寄存器约定：`a7`=调用号，`a0-a2`=参数，`a0`=返回值。
不需要移植 x86 的 `int 0x80` 压栈机制。

**第 2 步：内核分发**（`kernel/traps.c`）。ecall 时 `mepc` 停在
`ecall` 指令本身，必须 `mepc += 4` 才能回到下一条指令：

```c
case 8:   /* ecall from U-mode */
case 11:  /* ecall from M-mode（内核库） */
	{
		unsigned long nr = tf->a7;
		tf->mepc += 4;
		if (nr < NR_SYSCALLS)
			tf->a0 = sys_call_table[nr](tf->a0, tf->a1, tf->a2);
		else
			tf->a0 = -1;
		if (from_user)
			do_signals(tf);
	}
	break;
```

**第 3 步：用户态封装宏**（`include/unistd.h`）。原 x86 宏用内联
汇编触发 `int 0x80`，RISC-V 版本改为 `ecall`：

```c
#define _syscall3(type,name,atype,a,btype,b,ctype,c) \
type name(atype a, btype b, ctype c) { \
	register long __a7 __asm__("a7") = __NR_##name; \
	register long __a0 __asm__("a0") = (long)(a); \
	register long __a1 __asm__("a1") = (long)(b); \
	register long __a2 __asm__("a2") = (long)(c); \
	__asm__ volatile ("ecall" \
		: "+r" (__a7), "+r" (__a0), "+r" (__a1), "+r" (__a2) \
		: \
		: "memory", "t0", "t1"); \
	return (type) __a0; \
}
```

**第 4 步：声明 t0/t1 clobber（关键坑）。** trap 入口用 `t0/t1`
做临时寄存器，会覆盖用户态的值。汇编层的“保存现场”只保护 trapframe
里记录的寄存器；如果 C 编译器不知道 `t0/t1` 会被 clobber，就可能在
ecall 后继续使用旧值——表现为“输出每行只有一个字符”之类诡异现象。
对策就是在所有 ecall 内联汇编中显式把 `t0`、`t1` 声明为 clobber
（如上）。trap.S 中保存现场后、调用 C 之前，t0/t1 的值保存在
trapframe 的 `TF_X5/TF_X6` 槽位，恢复现场时原样写回，配合 clobber
声明即可保证语义正确。

### 7.4 验证方法

编译并运行 `t_up`（write 系统调用），预期输出 `done`；`getpid` 返回
非零且递增。

### 7.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 输出每行仅一个字符 | ecall 后 t0/t1 被 trap 入口覆盖 | 内联汇编声明 `"t0","t1"` clobber |
| 系统调用返回 -1 | 调用号或参数约定不一致 | 核对 `__NR_*` 与 `sys_call_table` 顺序 |
| fork 后子进程行为异常 | mepc 被加两次 | 只有 trap_handler 加一次，fork 复制 trapframe 时不要再加 |

## 8. 阶段七：ramdisk 与 Minix v1 根文件系统

### 8.1 目标

用宿主机构建工具生成 Minix v1 文件系统镜像，嵌入内核，启动时挂载为
根文件系统，shell 里能 `ls`、`cd`、执行程序。

### 8.2 涉及文件

| 文件 | 作用 |
|---|---|
| `tools/mkfs.c` | 宿主机工具：生成 Minix v1 镜像 |
| `rootfs.S`（构建生成） | `.incbin` 嵌入镜像 |
| `kernel/blk_drv/ramdisk.c` | ramdisk 块设备 |
| `fs/super.c` | `mount_root()` |
| `fs/bitmap.c` | 位图操作（`clear_bit` 语义） |
| `Makefile` | `rootfs.img`/`rootfs.S`/`rootfs.o` 规则 |

### 8.3 具体操作

**第 1 步：写 `tools/mkfs.c`。** Minix v1 布局（1 KB 块、14 位
zone 号、magic `0x137F`）：

```c
#define BLOCK 1024
#define NINODES 96
#define IMAGE_BLOCKS 2048      /* 2 MB 镜像 */
#define SUPER_MAGIC 0x137F
```

块 0 引导区、块 1 超级块、块 2 inode 位图、块 3 zone 位图、块 4 起
inode 表，之后是数据区。工具把所有用户程序 `.elf` 以固定名字（去掉
`.elf` 后缀）拷入 `/bin`，建立 `/bin`、`/dev` 目录和 `/dev/tty0`
字符设备节点，最后把 2 MB 缓冲区写盘。

**第 2 步：嵌入镜像（关键坑：必须用 `.incbin`）。**
`Makefile` 用 `printf` 生成 `rootfs.S`：

```make
rootfs.S: rootfs.img
	printf '.section .rootfs,"a",@progbits\n.globl _binary_rootfs_img_start\n_binary_rootfs_img_start:\n.incbin "rootfs.img"\n.globl _binary_rootfs_img_end\n_binary_rootfs_img_end:\n' > $@
```

不能对 `rootfs.img` 做 objcopy 转成 `.o` 再链接：objcopy 会把未初始化
区域填零，破坏镜像内容。`.incbin` 原样嵌入二进制，`ramdisk.c` 通过
`_binary_rootfs_img_start/_end` 符号访问。kernel.ld 的 `.rootfs` 段
（`KEEP(*(.rootfs))`）保证这段被保留。

**第 3 步：ramdisk 驱动**（`kernel/blk_drv/ramdisk.c`）。实现
`rd_init()` 和 `rd_request()`：把块请求直接映射为对嵌入镜像内存的
memcpy，`ROOT_DEV = 0x0101`（主设备 1=ramdisk，次设备 1），
`main()` 中 `rd_init(0,0)` 完成接线。

**第 4 步：修 `mount_root()` 的位图统计**（`fs/super.c`）。0.11
原版统计空闲块时用 `set_bit` 探测位图，会破坏位图导致“首次建文件就
空间不足”。RISC-V 移植改为只读探测：

```c
while (--i >= 0)
	if (!test_bit(i&8191, p->s_zmap[i>>13]->b_data))
		free++;
```

**第 5 步：确认 `clear_bit` 语义**（`fs/bitmap.c`）。0.11 的
`clear_bit` 是“若位原本为 0 则返回 1”（x86 `btr` 的进位标志语义），
与通用 Linux 内核相反。`free_block` 等代码依赖这一返回值判断“重复
释放”；RISC-V 移植必须保留原语义，不能“顺手修成标准语义”，否则位图
状态错乱。

### 8.4 验证方法

```sh
make -j2
make run
```

启动日志应出现 `xxx/2048 free blocks`、`xxx/96 free inodes` 和
`Free mem: ... bytes`；shell 里 `ls` 能看到 `bin`、`dev`。

### 8.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动 panic “Unable to mount root” | 镜像 magic 或布局不对 | 检查超级块字段与 `0x137F` |
| 首次 creat 报空间不足 | 位图被统计代码破坏 | 统计空闲用 `test_bit` 只读 |
| 挂载后数据全零 | objcopy 嵌入 | 改用 `.incbin` |

## 9. 阶段八：进程管理与 ELF 加载

### 9.1 目标

支持 fork（COW）、exit/wait、execve（加载静态 ELF 用户程序），
init 创建第一个用户进程 shell。

### 9.2 涉及文件

| 文件 | 作用 |
|---|---|
| `kernel/fork.c` | 复制 task_struct/trapframe、COW 页表 |
| `fs/exec.c` | ELF 解析、段映射、构造初始 trapframe |
| `user/crt0.S` | 用户程序入口（argc/argv 准备） |
| `init/main.c` | `init()`、`shell()` |

### 9.3 具体操作

**第 1 步：fork**（`kernel/fork.c`）。RISC-V 没有 x86 的 TSS，进程
切换信息全在 `task_struct.kctx`（ra/sp/s0-s11）和 trapframe 中。
fork 要点：

- 复制父进程 trapframe 到子进程栈顶（`PAGE_SIZE - TF_SIZE` 处）；
- `trap_handler` 已把 mepc 加 4（越过 ecall），fork 复制时**不得**
  再次加 4，否则子进程从错误地址继续；
- 子进程 `kctx.ra = ret_from_fork`，返回值处把 a0 置 0（父进程 fork
  返回 pid）；
- 页表用 `copy_page_tables()` COW 复制。

**第 2 步：exec**（`fs/exec.c`）。0.11 原版解析 a.out（`exec.c` 里的
`a.out.h` 结构），RISC-V 版改为解析 ELF32：

- 读 ELF 头，校验 magic `0x7f 'E' 'L' 'F'` 与 `e_machine==EM_RISCV`；
- 对每个 `PT_LOAD` 段，按 `p_vaddr/p_memsz/p_filesz` 分配并映射页，
  从文件拷贝内容，超出文件部分清零（BSS）；
- 把 `e_entry` 写入 `trapframe->mepc`；
- 正确设置 `end_code`（最后一个代码段的结束地址），否则 brk 边界
  错误，malloc 会异常；
- 构造初始 mstatus：`0x6088`（MPP=0 返回 U-mode、MPIE=1、MIE=1、
  FS=Dirty），对应 `include/linux/sched.h` 中 exec 的赋值：

```c
tf->mstatus = 0x6088;  /* MPP=0, MPIE=1, MIE=1, FS=Dirty */
```

- 命令行参数数组必须清零，避免无参数程序读到未初始化的 argv 项。

**第 3 步：用户程序入口**（`user/crt0.S`）。静态链接用户程序的
`_start` 从栈上取 argc/argv/envp 后调用 `main`：

```asm
_start:
	lw a0, 0(sp)      # argc
	addi a1, sp, 4    # argv
	addi a2, sp, 8    # envp
	call main
	call _exit
```

**第 4 步：init 启动 shell**（`init/main.c`）。`init()` 打开
`/dev/tty0` 三次（stdin/stdout/stderr），然后循环
`kernel_thread(shell)`；shell 执行 `execve("/bin/sh")` 成为第一个
用户进程。shell 退出后 init 打印退出码并重新拉起，所以 QEMU 不会
自己退出——CI 冒烟测试靠超时+日志断言。

### 9.4 验证方法

```sh
make run
```

预期出现 `Free mem` 等启动信息后进入 `sh#` 提示符；输入 `hello`
应打印 hello 程序输出；`t_fork`、`t_cow` 全部通过。

### 9.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 子进程反复异常 | fork 复制 trapframe 时 mepc 重复 +4 | 移除 fork 里的递增 |
| malloc 越界 | `end_code` 未设置 | exec 时按最后代码段结束地址赋值 |
| 程序输出乱码/参数错 | argv 未清零 | exec 时初始化参数数组 |
| 用户程序无法执行 | ELF 加载器还是 a.out | 改为解析 ELF32 PT_LOAD |

## 10. 阶段九：shell 与命令行交互

### 10.1 目标

提供可用的 shell：内置 cd/pwd/echo/ls/exit，其余命令按 `/bin/<cmd>`
查找执行；支持多行输入和退格编辑。

### 10.2 涉及文件

| 文件 | 作用 |
|---|---|
| `user/sh.c` | shell 主循环、内置命令、外部命令执行 |

### 10.3 具体操作

**第 1 步：命令解析与内置命令**（`user/sh.c`）。逐行读入、按空格
分词，`argv[0]` 匹配内置命令：

```c
if (!strcmp(argv[0], "exit"))  goto logout;
else if (!strcmp(argv[0], "cd"))    do_cd(argv[1]);
else if (!strcmp(argv[0], "pwd"))   /* 打印 getcwd */
else if (!strcmp(argv[0], "echo"))  do_echo(argv+1, i);
else if (!strcmp(argv[0], "ls"))    do_ls(argv[1] ? argv[1] : ".");
else { /* fork + execve("/bin/<cmd>")，失败打印 cmd not found */ }
```

**第 2 步：多行输入。** tty 一次 read 可能返回多行（例如粘贴），shell
循环里对缓冲逐行处理，不能默认“一次 read 一行”。

**第 3 步：外部命令。** `fork()` 子进程执行
`execve("/bin/" + argv[0])`；父进程 `waitpid`。执行失败返回 127。
这就是“`ls`、`cd` 这些是写死的内置命令，而 `t_fp` 等测试程序走
`/bin/` 外部加载”的设计。

### 10.4 验证方法

```sh
sh# cd bin
sh# pwd          # /bin
sh# ls           # 列出 rootfs /bin 下的程序
sh# ../bin/t_up  # 执行外部程序
sh# exit         # 打印 logout，init 重新拉起 shell
```

## 11. 阶段十：硬件浮点支持

### 11.1 目标

用户程序可以正常使用 F/D 浮点指令，浮点寄存器状态跨系统调用、信号、
调度切换保持正确。

### 11.2 涉及文件

| 文件 | 作用 |
|---|---|
| `Makefile` | `MARCH` 升级为 rv32imafdc / ilp32d |
| `include/linux/sched.h` | trapframe 增加 f0-f31（64 位）与 fcsr |
| `kernel/trap.S` | 保存/恢复浮点现场 |
| `fs/exec.c` | 初始 mstatus 含 FS=Dirty |
| `user/t_fp.c` | 浮点冒烟测试 |

### 11.3 具体操作

**第 1 步：升级工具链目标。** `MARCH` 从
`rv32imac_zicsr_zifencei` 改为 `rv32imafdc_zicsr_zifencei`，ABI 从
`ilp32` 改为 `ilp32d`（double 用寄存器传参）。

**第 2 步：trapframe 增加浮点区。** 在通用区后加 32 个 64 位槽
（`unsigned long long f[32]`，偏移 140-396）和 `fcsr`（偏移 396），
总大小 400 字节。trap.S 用 `.equ` 定义相同偏移（`TF_F0=140`、
`TF_FCSR=396`、`TF_SIZE=400`）。

**第 3 步：入口置 mstatus.FS=Dirty。** 保存 mstatus **之前**先把
FS 位（bits[13:14]）置为 3（Dirty），这样保存的 mstatus 里 FS 为
Off 的用户程序在返回后也能使用浮点指令：

```asm
	li t1, 3
	slli t1, t1, 13        # mstatus.FS = Dirty
	csrs mstatus, t1
	csrr t1, mstatus       # 再读（此时 FS=Dirty）
	sw t1, TF_MSTATUS(sp)
```

**第 4 步：用 64 位存取指令保存/恢复（关键坑）。**
`fsw/flw` 只操作寄存器低 32 位，会把相邻槽位搞乱。必须用 `fsd/fld`
逐条保存 f0-f31 和 fcsr：

```asm
	fsd f0, TF_F0(sp)
	fsd f1, TF_F0+8(sp)
	# ... f2-f31 ...
	csrr t3, fcsr          # t3 已保存过；保持 t0（from_user）不动
	sw   t3, TF_FCSR(sp)
```

**第 5 步：恢复顺序。** 恢复现场时先恢复浮点寄存器（此时还需要用
一个通用寄存器当基址，比如 t6），最后再恢复通用寄存器；特别是浮点
恢复**必须早于**恢复 x31（t6），否则会覆盖恢复用的基址指针。fcsr
同理在恢复通用寄存器前写回。

**第 6 步：exec 初始现场。** `fs/exec.c` 的初始 mstatus 用
`0x6088`（含 FS=Dirty），保证 exec 出来的用户程序直接能用浮点。

### 11.4 验证方法

```sh
sh# t_fp
```

t_fp 用迭代 `x = x*0.5 + 1.0`（收敛到 2.0），每 100 次迭代做一次
write 系统调用，最终把 double 的位模式打出来。预期输出固定为
`4000000000000000`。若浮点现场保存出错，中间值或最终值会变。

### 11.5 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户程序非法指令（cause=2） | FS 未开启或工具链没带 F/D | 入口置 FS=Dirty；`MARCH` 用 rv32imafdc |
| 浮点结果错乱 | 32 位 fsw/flw 破坏 64 位槽 | 改 fsd/fld |
| 恢复后 t6 错乱 | 先恢复了 x31 再恢复浮点 | 浮点恢复提前到通用寄存器之前 |
| fcsr 被污染 | 用 t0 读 fcsr 覆盖了 from_user | 用已保存的 t3，保持 t0 不动 |

## 12. 阶段十一：控制台与终端稳定性

### 12.1 目标

长时间输出不丢失；逐字符输入不阻塞；退格能正常删除字符。

### 12.2 涉及文件

| 文件 | 作用 |
|---|---|
| `include/asm/system.h` | `save_flags/restore_flags` |
| `kernel/chr_drv/tty_io.c` | `tty_read` 整行轮询、退格处理 |
| `kernel/chr_drv/console.c` | 串口轮询输入 |

### 12.3 具体操作

**第 1 步：cli/sti 嵌套安全。** x86 的 cli/sti 是标志位，0.11 大量
代码 `cli(); ...; sti();` 直接配对。RISC-V 的 mstatus.MIE 没有
嵌套计数，内层 `sti()` 会把外层关掉的全局中断提前打开。移植改为
保存/恢复：

```c
static inline unsigned long save_flags(void)
{ return mstatus & 8; }          /* MIE 位 */

static inline void restore_flags(unsigned long f)
{ if (f) sti(); else cli(); }
```

把原来裸 `cli()/sti()` 配对的临界区改成
`save_flags()/restore_flags()`。否则长时间输出时嵌套调用会失衡，
表现为输出丢字或中断永不开启。

**第 2 步：tty_read 轮询整行。** canonical 模式下 read 要求返回完整
一行。x86 靠键盘中断+队列，RISC-V 版直接轮询 UART 直到收到换行符
（`kernel/chr_drv/console.c` 的 `poll_uart()`，在 `tty_read` 里循环
调用）。若只读一次就返回，会出现“输入一个字符就卡住”的问题。

**第 3 步：退格。** 0.11 默认删除键是 DEL（`0x7f`），但 QEMU
终端/终端模拟器发的是 BS（`0x08`）。tty 的擦除处理两者都接受，且
启用 ECHOE（回显 `\b  \b` 擦除）：

```c
if (c == ERASE_CHAR(tty) || c == 8) {   /* DEL 或 BS */
	if (L_ECHOE(tty)) { /* 回显擦除序列 */ }
}
```

### 12.4 验证方法

- 连续打印大量文本（例如反复执行 `t_up`）无丢字；
- 逐字符输入命令不卡顿；
- 输入 `abc` 后按退格两次再输 `d`，最终命令行显示 `ad`。

## 13. 阶段十二：测试程序与压力测试

### 13.1 目标

用一组测试程序覆盖各子系统，做功能全量测试和压力测试。

### 13.2 测试程序清单

全部位于 rootfs 的 `/bin` 下，shell 里直接输入名字运行：

| 程序 | 覆盖点 | 预期 |
|---|---|---|
| `t_up` | 系统调用封装/输出 | 打印后输出 `done` |
| `t_fp` | 浮点跨 trap 正确性 | 输出 `4000000000000000` |
| `t_fork` | fork/exec/wait | 打印 pid 后 `fork test done` |
| `t_cow` | COW、堆增长 | 父子数据各自独立 |
| `t_fs` | 文件读写、目录 | 创建/读回一致 |
| `t_pipe` | 管道通信 | 父子通过管道收发成功 |
| `t_sig` | 信号处理 | alarm/kill 触发处理函数 |
| `t_sched` | 多进程调度 | 多进程交替执行、计数正确 |
| `t_stress` | 综合压力（FS/堆/管道/COW 并发） | 全部完成且结果一致 |
| `t_hello` | 最小 ELF 加载 | 打印 hello |
| `extprog` | 外部编译的静态 ELF 可执行 | 直接放入 rootfs 可运行 |

### 13.3 手动全量测试

```sh
make run
sh# t_up
sh# t_fp
sh# t_fork
sh# t_cow
sh# t_fs
sh# t_pipe
sh# t_sig
sh# t_sched
sh# t_stress
```

压力测试可叠加多实例：

```sh
sh# t_stress
sh# t_stress &
sh# t_fs & t_pipe & t_sched &
```

（0.11 的 shell 支持 `&` 后台与 `wait`；详见 `docs/测试指南.md`。）
判定标准：每个程序输出符合预期且无 panic、无 “kernel trap” 打印、
无 `free page` panic。

## 14. 阶段十三：CI 与版本发布

### 14.1 目标

每次推送自动构建+冒烟测试；打 `v*` 标签自动发布 GitHub Release。

### 14.2 涉及文件

| 文件 | 作用 |
|---|---|
| `.github/workflows/build.yml` | push/PR 触发：装工具链→构建→QEMU 冒烟→上传产物 |
| `.github/workflows/release.yml` | 推 `v*` 标签触发：构建+冒烟+打包发布 |

### 14.3 具体操作

**build.yml** 的核心冒烟测试（QEMU 因 init 重生 shell 永不退出，
所以用超时+日志断言，不用退出码）：

```sh
( sleep 8; printf 't_up\n'; sleep 3; printf 'exit\n'; sleep 3 ) \
  | timeout 25 qemu-system-riscv32 -M virt -m 128M -bios none \
      -kernel kernel.elf -nographic -monitor none -serial stdio 2>&1 \
  | tee /tmp/boot.log || true
grep -q "fork test pid=" /tmp/boot.log
grep -q "done" /tmp/boot.log
grep -q "logout" /tmp/boot.log
```

**release.yml** 在 build 基础上增加 `permissions: contents: write`，
用 `softprops/action-gh-release` 之类的步骤把
`rv011-vX.tar.gz + SHA256SUMS` 发布为 Release。

### 14.4 发布流程

```sh
git tag -a v0.1.1 -m "release v0.1.1"
git push origin v0.1.1
```

推标签后等待 Actions 完成，Release 页面出现产物。当前已发布 v0.1.0
和 v0.1.1。
